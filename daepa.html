CASE STUDY 01

대파, AI 채팅 서비스를 위한
AWS 인프라

서비스 API부터 AIChat·LLM Worker까지, 애플리케이션을 실행하는 인프라 전체를 Terraform으로 구성했습니다.

기간 / 소속2025.06 – 2026.05 / 씨피랩스
프로젝트 인원10명
역할AWS 인프라 구축·운영 / 배포 자동화
핵심 기술Terraform · ECS Fargate · Bedrock
프로젝트와 담당 범위서비스 아키텍처주요 설계 선택Terraform과 배포 자동화이미지 처리와 AI 연계

프로젝트와 담당 범위

대파는 사용자와 AI의 대화, 페르소나와의 대화 및 추천 기능을 제공하는 서비스입니다. 기능별 Agent와 Worker를 포함한 서버들이 함께 동작할 AWS 환경을 구성했습니다.

서비스 API, WebSocket, 알림 Consumer, AIChat, LLM Worker를 각각 별도 ECS 서비스로 구성했습니다. 네트워크와 데이터 저장소, Bedrock 연계 자원 등 관련 인프라를 Terraform 모듈로 관리하고 컨테이너 배포 흐름을 구축했습니다.

서비스 아키텍처

서울 리전의 공유 VPC에서 두 가용 영역(ap-northeast-2a·2c)에 Fargate 태스크를 배치했습니다. 외부 요청을 받는 계층과 내부 실행 환경을 구분했습니다.

주요 설계 선택

01 / 외부 진입점

환경별 ALB 하나를 공유

서비스를 분리하면서 ALB 비용을 함께 고려했습니다. 환경별 ALB 하나를 공유하고 호스트 기반 라우팅으로 API와 WebSocket의 Target Group을 구분했습니다. ALB에는 WAF와 ACM 인증서를 연결했습니다.

02 / 실행 환경

서비스별 Fargate와 Service Connect

API, WebSocket, 알림 Consumer, AIChat, LLM Worker의 실행 단위를 각각 분리했습니다. 내부 서비스 통신에는 Service Connect를 사용하고, AIChat·Worker·알림 Consumer에는 외부 진입용 ALB를 직접 연결하지 않았습니다.

03 / 데이터 계층

Aurora를 공유하고 스키마로 구분

Aurora MySQL은 Writer 1대와 Reader 2대로 구성했습니다. 서비스 데이터와 Job Pool은 하나의 Aurora 환경에서 스키마 단위로 구분했습니다. MQ는 RabbitMQ 클러스터, Redis는 ElastiCache 클러스터로 구성했습니다.

04 / 네트워크 경계

Private Subnet 배치와 외부 통신 경로

ECS와 DB를 Private Subnet에 배치했습니다. 외부 API 호출에는 환경당 NAT Gateway 하나를 사용하고, VPC 내부의 S3 접근에는 VPC Endpoint를 적용했습니다.

Terraform과 배포 자동화

관련 인프라를 Terraform 모듈 단위로 나누어 관리했습니다. 구축 환경과 운영 문서를 남겼고, 퇴사 이후에도 구성원들이 이를 활용하고 있습니다.

  1. Bitbucket Pipelines애플리케이션 컨테이너 이미지 빌드
  2. Amazon ECR빌드한 이미지 업로드
  3. Amazon ECS서비스에서 실행할 Task 구성 갱신

이미지 처리와 AI 연계

이미지에는 별도의 CloudFront·Lambda@Edge·S3 경로를 구성했습니다. 요청 파라미터에 맞춰 이미지를 리사이징하고 변환 결과를 S3에 저장했습니다.

LLM Worker는 Bedrock Agent를 호출합니다. Agent의 Action Group에는 Lambda가 연결되며, Knowledge Base와 OpenSearch, Context·Persona용 S3를 포함한 연계 인프라를 구성했습니다.
